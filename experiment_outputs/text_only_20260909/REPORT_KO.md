# 텍스트 문서 기반 검색·충돌 처리 개선 보고

실험일: 2026-09-09. 결과: 검색과 충돌 후보 판별은 개선됐지만, 검색부터 답변까지의 충돌 보고는 아직 4개 실패 사례가 남는다.

## 수정 내용

- `search_service.py`: 질문 표현을 규정 용어로 확장했다. 예: minimum attendance → quorum. Hybrid 점수에 BM25를 명시적으로 결합하고, BM25 35% + 로컬 LSA 35% + lexical 20% + reranking 10%로 조정했다. 명시적으로 구속력 없는 참고 설명은 낮은 점수를 주었다. BM25/Dense/RRF 개별 비교 모드는 유지했다.
- `policy_claim_service.py`: 숫자·금지 표현 비교 외에 필수 경력의 대체 허용, 승인 전 활동 시작, 의무 활동의 예외 허용을 잠재적 충돌로 표시하도록 추가했다. 부정문과 이미 예외가 있는 규칙을 구분하는 테스트도 추가했다.
- `rag_service.py`: 충돌 질문에는 인접 문장까지 보존해 조건이 잘리는 문제를 줄였다. 후보 자격을 비교할 때 지원하는 직책과 과거 경력 직책을 구분해 다른 직책의 충돌이 잘못 연결되는 것을 줄였다.
- `text_only_benchmark.py`: 운영 인덱스를 변경하지 않는 별도 실험을 만들고 원문·코드 해시, 질문, 검색 결과, 인용, 실패 사례를 저장했다.

## 데이터와 평가 방식

금융 매뉴얼은 제외했고 OCR은 사용하지 않았다. Derived Governance와 Synthetic Conflict PDF 두 개에서 텍스트를 직접 추출했다. 원본 파일은 삭제하거나 수정하지 않았다.

- Derived의 기본 레코드 57개 + Synthetic의 기준/충돌/무관 레코드 60개 = 117개 검색 단위.
- Derived의 반복 확장 내용과 질문·정답 영역, Synthetic의 정답 해설은 검색 인덱스에서 제외했다.
- 제목 기반 질문 57개, 표현을 바꾼 질문 15개, 충돌 질문 20개를 5개 검색 방식으로 평가했다: 단계별 460회.
- 충돌 판별 별도 검사 80개: 문서 간 20개, 동일 문서 20개, 동일 내용 20개, 무관 설명 20개.
- Hybrid 답변 전체 흐름 20개: 경고 여부뿐 아니라 의도한 양쪽 문서의 인용이 함께 있는지 확인했다.
- 로컬 LSA와 규칙 기반 답변을 사용했다. LLM 생성 성능이나 외부 API는 테스트하지 않았다.

## 수정 전후 결과

동일한 질문·문서로 저장한 `before`와 `after` 비교다. 아래 검색 수치는 Hybrid 결과다.

| 평가 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 제목 기반 질문: 정답 레코드 상위 5개 포함 | 57/57 | 57/57 |
| 표현 변경 질문: 정답 레코드 상위 5개 포함 | 9/15 (60.0%) | 13/15 (86.7%) |
| 표현 변경 질문 MRR@10 | 0.443 | 0.739 |
| 충돌 양쪽 레코드 상위 5개 포함 | 10/20 (50%) | 14/20 (70%) |
| 올바른 양쪽 근거를 직접 제공한 문서 간 충돌 판별 | 17/20 | 20/20 |
| 검색→답변에서 목표 충돌 쌍 보고 | 14/20 (70%) | 16/20 (80%) |

수정 후 동일 문서 충돌 20/20을 탐지했다. 동일 내용/무관 설명 40개에서는 충돌을 표시하지 않았다. 답변 20개의 반환 인용은 해당 검색 원문과 일치했다. 이는 답변 자체의 정답률이나 모든 현실 문서에서의 오탐률을 뜻하지 않는다.

## 아직 남은 문제

전체 답변 흐름에서 실패한 시나리오는 01 BoG quorum, 09 President-Elect eligibility, 15 New TC approval, 20 Governance hierarchy다. 올바른 근거를 직접 제공하면 판별되지만 검색·근거 선택을 포함하면 목표 충돌 쌍이 누락된다. 따라서 충돌 판별만으로 전체 시스템을 100% 정확하다고 보고하면 안 된다.

다음 개선 대상은 질문의 주제·직책·조건과 근거 문장을 더 정확히 연결하고, 상위 단일 근거 중심 선택 대신 관련 규칙 쌍을 비교하는 것이다. 새 변경은 별도 미사용 holdout 질문과 현실적인 비충돌 사례로 검증해야 한다.

## 해석상 주의

- 이 결과는 개발용 합성 데이터에서 관찰한 개선이다. 실패 사례를 보고 규칙과 표현 확장을 조정했으므로 독립적인 최종 평가가 아니다.
- 제목 기반 질문은 쉬운 평가이며, 정답 ID를 기준으로 채점하므로 의미가 같은 다른 레코드를 찾은 경우도 실패로 집계될 수 있다.
- 합성 레코드의 authority 값과 승인 상태는 실험용 가정이다. 운영 문서 등록부나 ChromaDB를 변경하지 않았으며 합성 문서를 실제 승인된 정책으로 취급하면 안 된다.
- 새로운 규칙은 확정 판결이 아니라 검토할 잠재적 충돌을 찾는다. 사람이 문서 상태·적용 조건을 확인해야 한다.
- 실행 시간은 환경 영향을 받으므로 속도 향상을 주장하지 않는다.

## 재현

프로젝트 루트에서 실행한다. 기존 결과를 보존하려면 새 stage 이름을 사용한다.

```sh
OPENBLAS_NUM_THREADS=1 ./venv/bin/python -m experiments.text_only_benchmark --stage verification
./venv/bin/python -m unittest tests.test_policy_exceptions tests.test_policy_claims tests.test_authority_conflicts tests.test_vertical_slice tests.test_hybrid_rag tests.test_response_cache -q
```

`before/`는 수정 전 결과이고, 현재 코드로 실행하면 수정 후 동작을 재현한다. 각 폴더의 `manifest.json`에 데이터와 핵심 코드 해시가 있다. `summary.json`, `retrieval_cases.json`, `pairs.json`, `chats.json`에서 세부 결과를 확인할 수 있다. Git commit/push는 수행하지 않았다.
